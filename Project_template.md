# RAG‑бот для QuantumForge Software: анализ, сравнение стеков и рекомендации

## Введение

### Контекст компании

* Продукт: SaaS‑платформа «Digital Twin», плюс консалтинг (≈20% оборота).
* Инфраструктура: AWS (EKS + RDS), edge‑ноды, Kafka, ClickHouse, Snowflake; CI/CD на GitHub Actions/Jenkins/ArgoCD; Confluence/Google Drive/Jira/Slack/Miro; Monorepo (Python/Go/Node), ADR/MDX, dbt‑доки.
* Объём знаний: ≈18 000 Markdown/MDX, ≈3 000 Confluence‑страниц, ≈250 PDF‑спецификаций; прирост ≈400 стр./мес.
* Пользовательские роли: разработчики, саппорт, менеджеры/аналитики, новые сотрудники.
* Боли: дубли/рассинхронизация, долгий поиск, быстрый «drift» после релизов, дорого готовить SOC 2.

### Требования к боту

1. Персонализированные точные ответы из корпоративной базы знаний (RAG).
2. Подсветка пробелов в документации (gap‑analysis) и метрики качества.
3. Масштабируемость (от отдела R&D ко всей компании и, при желании, к внешним клиентам).
4. Сокращение TTM и FTE‑затрат на поиск/коммуникации; помощь в SOC 2.

### Ограничения и приватность

* Материалы разной степени чувствительности; часть нельзя выносить в облако.
* Требования к аудиту/трассируемости (SOC 2), контроль версий.
* Интеграции: Slack, Confluence, GitHub, Zendesk, Jira, ClickHouse/Snowflake.

### Риски

* Утечки через промпты/логирование, компрометация секретов.
* Инъекции в источниках (prompt injection).
* Расхождения версий документации (stale/duplicated content) → неверные ответы.

## Сравнение LLM‑моделей: локальные (Hugging Face) vs облачные (OpenAI / YandexGPT)

### Качество ответов

* Облачные (OpenAI, линейка GPT): обычно лучшая фактическая точность, устойчивость к «prompt injection», более сильные навыки рассуждения и следование инструкциям. Хорошо подходят для сложных запросов разработчиков и GRC.
* Локальные (Llama‑семейство, Mistral/Mixtral, Qwen, Phi‑3 на HF): при грамотной настройке + хороших промптах дают отличные ответы для внутренней базы, особенно с сильным RAG и reranker’ом. Для сложных рассуждений и мультимодальности часто уступают флагманам в облаке; зато полностью контролируемы.

### Скорость

* Облако: как правило, ниже латентность «холодного старта», высокая стабильность; но зависит от региона/сетей.
* Локальные: при наличии GPU на месте латентность отличная и предсказуемая; на CPU‑только — хуже.

### Стоимость владения/использования

* Облако: OpEx по токенам. Мини‑модели дают очень низкую цену за миллион токенов; при пиках — удобно масштабировать. Но нужны меры DLP и соглашения по данным.
* Локальные: CapEx на GPU/узлы + OpEx на админку/поддержку/обновления. Выгодно при стабильной большой нагрузке, строгой приватности, и если нужны on‑prem гарантии.

### Развёртывание и удобство

* Облако: быстрее старт (SDK/API), готовые политики и мониторинг.
* Локальные: Helm‑чарты/Operator, inference‑серверы, логирование/обновления; выше DevOps‑сложность, но гибкость максимальная.

**Вывод**: для QuantumForge целесообразны гибридные сценарии: приватные/секретные данные обслуживать локальной LLM, а универсальные/низкосекретные запросы — облачной недорогой моделью.

## Сравнение моделей эмбеддингов: локальные Sentence‑Transformers vs облачные OpenAI Embeddings

### Скорость индексации

* Локальные: при наличии 1× GPU можно за ночь прогнать 20–40 млн токенов; горизонтально масштабируются (шардинг документов). На CPU — существенно медленнее.
* OpenAI Embeddings: высокая скорость без своей инфраструктуры, хорошо бьётся батчингом; сеть — узкое место.

### Качество поиска

* OpenAI text-embedding-3 (small/large): сильные универсальные векторы (англ./мультияз), устойчивые на длинных технических текстах. Хорошо работают на смешанном домене (коды + доки).
* Локальные ST (например, bge-large-en, bge-m3, gte-large, e5-large-v2, мультиязычные LaBSE/bge-m3): в домене "инженерная документация" дают сопоставимое качество при тонкой настройке и правильном препроцессинге. Плюс есть приватность и отсутствие токенных затрат.

### Стоимость владения
* Облако: оплата per‑token/символ. Для разовой массовой индексации бюджета может хватить, далее — ежемесячный прирост (~400 стр.)
* Локальные: амортизация GPU + поддержка; выгодно при регулярных переиндексациях и больших объёмах, а также при строгих DLP.
  
**Вывод:** для первой итерации — OpenAI embeddings (быстрый старт и сильное качество). Для зрелости/приватности — перевести на локальные ST.

## ChromaDB vs FAISS (векторный слой)

**FAISS** — это библиотека ANN‑поиска, без «БД‑фич»: нет сервера, коллекций/аутентификации/TTL/удобной метадаты «из коробки».
**ChromaDB** — это векторная БД (постоянное хранение, коллекции, фильтры по метаданным, HTTP‑API, клиент‑сервер режим, интеграции с LangChain/LlamaIndex/Haystack, локальная и облачная версии).

### Скорость поиска/индексации
FAISS: лидер по «сырой» скорости на миллиардных масштабах, гибкие индексы и тюнинг.
ChromaDB: «достаточно быстро» для 10^5–10^8 векторов; в реальных RAG‑ботах узким местом чаще становится reranking/LLM, а не сам ANN.

### Внедрение и поддержка
FAISS: потребуется собственная «надстройка» (файловая/СУБД‑персистентность, схемы метадаты, API, ACL, бэкапы, миграции).
ChromaDB: из коробки коллекции/персистентность/HTTP‑клиент/фильтры; легче для команды приложений.

### Удобство работы
ChromaDB: простой SDK, развёртывание как сервиса, понятные бэкапы; есть Chroma Cloud (для несекретных данных).
FAISS: максимальная гибкость/производительность ценой дополнительной инженерной надстройки.

### Стоимость владения
ChromaDB self‑hosted: CPU/диск + DevOps; Cloud — по объёму/операциям.
FAISS: самая низкая сырьевая стоимость, но выше инженерные затраты на «обвес» (API/операции/безопасность).

**Вывод**: Для текущего масштаба и скорости внедрения более оптимальным представляется выбор ChromaDB как основного векторного слоя.

## Серверные конфигурации для развёртывания

Все конфигурации предполагают Kubernetes (EKS) и раздельные узлы для «retrieval» и «генерации». Диски — gp3/io2; сетка — ENA 25–50 Gb/s; observability — Prometheus/Grafana 

### A. CPU‑только (минимум, без локальной генерации)

Узел Retrieval: 8 vCPU, 32–64 GB RAM, NVMe 500 GB.

Сервисы: парсинг/ингест, ChromaDB, BM25, лямбда‑воркеры для Confluence/GitHub/Drive, OpenAI/YandexGPT как внешние LLM.

Где уместно: быстрый пилот, SOC 2 без требований on‑prem генерации.

### B. Гибрид (локальные эмбеддинги + облачная генерация)

Узел Retrieval‑GPU: 16 vCPU, 64–128 GB RAM, GPU 1× L4/RTX 4090, NVMe 1–2 TB.

Сервисы: локальные Sentence‑Transformers на GPU, ChromaDB, reranker (Cross‑Encoder), облачная LLM для ответа.

Где уместно: приватность эмбеддингов/метадаты + низкая латентность поиска.

### C. Полностью локальная генерация (он‑прем LLM)

Узел Gen‑GPU: 32 vCPU, 128–256 GB RAM, GPU 1–2× L40S, NVMe 2–4 TB.

Узел Retrieval‑GPU: 16 vCPU, 64–128 GB RAM, GPU 1× L4/A10G, NVMe 1–2 TB.

Сервисы: vLLM/TGI для Llama‑класса (8–70B, возможно QLoRA/quantization), локальные эмбеддинги/реранкер, ChromaDB.

Где уместно: строгая DLP (NDA/секретка), стабильная большая нагрузка.

## Варианты решения

### Вариант 1 — Cloud‑first (минимальная сложность)

* LLM: облачная «mini»‑модель + «large» по эскалации.
* Эмбеддинги: облачная модель.
* Векторная БД: Chroma Cloud (несекретные), либо self‑hosted Chroma в EKS (секретные).
* Плюсы: быстрый запуск (недели), низкий CapEx, легко масштабировать.
* Минусы: данные и токены уходят в облако; юрисдикция/комплаенс; сетевые задержки.
* Когда выбирать: пилот/PoC, несекретные домены, быстрый ROI.

### Вариант 2 — Гибрид (локальные эмбеддинги + облачная генерация)

* LLM: облачная «mini/large».
* Эмбеддинги: локальные Sentence‑Transformers на GPU (bge‑m3 / e5‑large‑v2) + опционально резервный облачный индекс.
* Векторная БД: ChromaDB self‑hosted (PersistentClient + HTTP API), бэкапы в S3.
* Плюсы: приватность индекса, низкая латентность retrieval, умеренная сложность.
* Минусы: нужен GPU‑узел и MLOps для эмбеддингов.
* Когда выбирать: большинство внутренних запросов, средняя/высокая приватность.

### Вариант 3 — On‑prem (полностью локально)

* LLM: локальная Llama‑класса (8–70B).
* Эмбеддинги: локальные ST; reranker — локальный cross‑encoder.
* Векторная БД: ChromaDB self‑hosted; при росте >100 млн векторов — рассмотреть Qdrant + FAISS в качестве движка.
* Плюсы: максимум контроля/приватности.
* Минусы: наибольшая инженерная сложность и CapEx.
* Когда выбирать: строгие DLP/юрисдикции, большой стабильный трафик.

## Рекомендации по выбору инструментов

**Векторная БД**:

* Брать ChromaDB как основной слой: коллекции, персистентность, фильтры, HTTP‑API, простая интеграция с LangChain/LlamaIndex. Для будущего масштабирования — держать в голове миграцию на Qdrant; внутри Chroma можно выбрать бэкенд хранения и настроить шардирование.

**Эмбеддинги**:

* Этап 1 (запуск): облачные OpenAI embeddings (высокое качество, быстрый старт).
* Этап 2 (зрелость/приватность): локальные bge-m3 (мультияз) или e5-large-v2 (англ.‑ориентированный), с периодическим A/B‑замером качества.

**LLM‑модели**:

* Для дефолтных ответов (Slack‑бот, Zendesk‑ассистент): «мини‑модель» в облаке для низкой цены/латентности.
* Для сложных инженерных запросов: «большая» модель по эскалации (trigger по низкому уверенному скору/«не нашёл»).
* Для приватных контентов: опциональный локальный inference.

### Итоговый выбор для QuantumForge (рекомендуемый вариант)

**Основной (рекомендованный): Вариант 2 — Гибрид**

**Почему**: баланс приватности, стоимости и времени запуска. Эмбеддинги и поисковый слой — локально (низкая латентность, без выноса исходного текста). Генерация — недорогая облачная «mini»‑модель с авто‑эскалацией на «large» для сложных кейсов.
